# 0021 — User domain — profile & settings

- **Status:** Accepted
- **Date:** 2026-09-12
- **Origin:** migrated verbatim from `CLAUDE.md` on 2026-10-27. Body kept as written; later corrections appear as dated notes, not edits.


Built on branch `userSettings`, 2026-09-12. Until now `user` was the one domain without a Controller/Service/impl — just `User`, `Role`, `UserRepository`, `UserMapper`, `UserResponse` — and "the profile" was `GET /auth/me` on `AuthController`, mapping in the controller. This gave `user` the standard layout and moved the profile under `/api/users/me`. Trigger: the frontend wants a profile page (photo, names, email, totals, best streak, notification toggle, registration date) and a settings page (edit photo/names/email/password).

Framing that shaped the design — the frontend's list bundles four different backend concerns:

- **`User` fields** (names, email, `createdAt`) → this domain, trivial.
- **Cross-domain aggregates** (total events/tasks, best habit streak) → **frontend composes, no backend**: `GET /api/tasks` and `GET /api/calendar/events` already return `Page` (`totalElements` with `size=1`), `GET /api/habits` returns `longestStreak` per habit. A `GET /me/stats` with `UserServiceImpl` calling `TaskService`/`EventService`/`HabitService` was weighed and declined: `user` is the foundation every domain depends on, and having its service depend back on Task/Event/Habit inverts that direction for a vanity number. Same "pure composition, no backend aggregator" stance as the agent's unified agenda. "Total tasks" = tasks ever created, all statuses (decided with the user).
- **Notification toggle** → **frontend move only**: it's `POST/DELETE /api/notifications/subscribe`, a *per-browser* push subscription, not a user preference — a profile page showing it as "Notificaciones: activadas" will read as user-level and isn't. A real user-level flag (`User.notificationsEnabled` checked in `NotificationServiceImpl.notify`) is a different feature, not built.
- **Photo** → its own step (below); the only item that brought new infrastructure.

Decisions made:

- **Separate endpoints per kind of change, not one `PUT /me` with optional fields.** Names, email, and password have different validation, different security (the last two require `currentPassword` — a token proves someone holds the session, not that they're the owner) and different side effects. A single PUT with nulls would force `if (request.password() != null)` branches in the service.
- **Read maps the principal, writes reload it.** `getProfile` maps `@AuthenticationPrincipal User` directly — the JWT filter loaded that exact row from the DB milliseconds earlier; re-fetching would return the same row (the one query it does make is `existsByUser` for `hasAvatar`). Every write goes through `findManaged` (`repository.findById(user.getId())`, `ResourceNotFoundException` on miss) and mutates the managed instance inside the transaction — the principal is a detached entity loaded outside any service transaction, and the `changePassword`/`changeEmail` checks must compare against what's in the DB *now*. A test (`updateProfile_escribe_sobre_la_instancia_recargada_y_no_sobre_el_principal`) exists specifically so this asymmetry isn't "simplified" away.
- **`@ValidPassword` (`common.validation`)** — a composed Bean Validation constraint (`@NotBlank` + `@Size(8..25)` + `@Pattern`, `validatedBy = {}`, no `@ReportAsSingleViolation` so each rule keeps its own message). Extracted because `RegisterRequest.password` and `PasswordUpdateRequest.newPassword` need the *same* rule and duplicating annotations is how the two drift apart. The `@AssertTrue isPasswordConfirmed()` was deliberately **not** extracted — a two-line record method comparing its own fields; a class-level validator would cost more than the repetition. `RegisterRequestTest` (pre-existing, 8 cases) is the regression net proving the composed constraint applies to record components after the swap.
- **`currentPassword` is `@NotBlank` only, never `@ValidPassword`.** It's the password the user already has; if the policy is ever tightened, their old one might not satisfy it and they'd be locked out of changing it. A test guards this against "fixing" it for symmetry.
- **Changing the password does not invalidate any session** — the JWT doesn't depend on the password and there's no revocation list (single user, no refresh tokens). Not rejecting `new == old` either; no case behind it.
- **`changeEmail`: password check first, availability check second** — a test asserts `existsByEmail` is never reached on a wrong password, so the endpoint can't be used as an "is this email registered?" oracle without credentials. Same email as current → idempotent no-op (otherwise `existsByEmail` reports "already registered" against the user's own address). `existsByEmail` gives the clean message; `uk_user_email` (V12) is the actual guarantee under a race — and that race now lands as **409**, not 500, via the new `DataIntegrityViolationException` handler (below). Thanks to the id-subject JWT, **no token is re-issued**.
- **Avatar in Postgres (`bytea`), in its own 1:1 table `user_avatars` (`V19`), never a column on `users`.** `CustomUserDetailsService.loadUserById` loads `User` on every authenticated request — a blob there would travel with every API call. Same migration shape as `V14` (`UNIQUE(user_id)` + `ON DELETE CASCADE` declared in SQL since `validate` checks neither). Entity uses `byte[]` **without `@Lob`** — `@Lob` on Postgres maps to `oid` (large objects with their own cleanup semantics); bare `byte[]` maps to `bytea`, which is what the migration creates. External object storage: not until the avatar stops being the only image in the system. Backups: `pg_dump` covers it for free — a file on disk wouldn't have been in any backup.
- **Backend does not resize; the frontend does (~256×256 before upload).** Two size limits with different roles: `UserServiceImpl.MAX_AVATAR_BYTES = 512 KB` is the *rule* (`BusinessException` → 400 with a message); Spring's default `spring.servlet.multipart.max-file-size` (1 MB) is the *guard* so an absurd payload never reaches memory (→ 413 via the new `MaxUploadSizeExceededException` handler). Allowed types: `image/jpeg`, `image/png`, `image/webp`. Adding an image library for one use case was declined.
- **`MultipartFile` never enters the service.** It's a Spring Web type; the controller unpacks it into `dto/AvatarContent(contentType, byte[] data)` — a neutral record that is also `getAvatar`'s return type. Same rule that keeps Gemini DTOs inside `ai.llm.gemini`, applied to HTTP transport.
- **`GET /api/users/me/avatar` returns raw bytes with the image's `Content-Type` — the only endpoint in the project that doesn't return `ApiResponse<T>`.** `ApiResponse` wraps JSON; an image isn't JSON, and base64-in-JSON was the alternative explicitly rejected. `UserResponse.hasAvatar` tells the frontend whether to fetch it (`UserMapper.toResponse(User, boolean hasAvatar)` — second mapper after `HabitMapper` with a computed extra source parameter).
- **`DataIntegrityViolationException` → 409, `MaxUploadSizeExceededException` → 413** in `GlobalExceptionHandler`. Both are infrastructure exceptions with a precise HTTP meaning that were falling into the generic 500 catch-all. The 409 handler is deliberately generic — no constraint-name inspection, no schema-name-to-message mapping; the constraint goes to a `log.warn`, the client gets "conflicto con datos existentes". It covers UNIQUE/FK/CHECK/NOT NULL alike (a CHECK reaching the DB would strictly be a 400, but every CHECK is pre-validated at DTO/service level, so reaching it means a race or a bug either way). Collateral fix: `register`'s own email race also moved from 500 to 409 without touching `AuthServiceImpl` — the argument for putting it in `common`. Does not collide with `LlmCredentialInvalidException`'s 409: the frontend discriminates by status *within an endpoint*, and BYOK is dormant.

Implemented (`/api/users/me`, all behind `anyRequest().authenticated()` — which also fixed a pre-existing bug: `/auth/**` is `permitAll`, so `GET /auth/me` without a token returned **200 with `data: null`**, not 401):

- `GET /me` → `UserResponse` (now with `createdAt`, `hasAvatar`). `AuthController.me` deleted; `align-web` must switch to the new URL.
- `PUT /me` (`ProfileUpdateRequest`: `firstName`/`lastName`, same rules as `RegisterRequest`; `UserMapper.updateEntity` — the record's shape is what limits which columns get written, no `if`).
- `PUT /me/password` (`PasswordUpdateRequest`: `currentPassword`, `newPassword`, `confirmPassword`) → `ApiResponse<Void>`.
- `PUT /me/email` (`EmailUpdateRequest`: `newEmail`, `currentPassword`) → `UserResponse`.
- `PUT /me/avatar` (multipart, part name `file`), `GET /me/avatar` (bytes), `DELETE /me/avatar` (idempotent, like `unsubscribe`). `saveAvatar` is an upsert (`findByUser().orElseGet(new)`), same idiom as `PushSubscriptionServiceImpl.subscribe`.
- `UserServiceImpl`: class-level `@Transactional(readOnly = true)`, explicit override on every write, explicit constructor (`UserRepository`, `UserAvatarRepository`, `UserMapper`, `PasswordEncoder`). Private helpers `findManaged`, `verifyCurrentPassword`, `toResponse` (mapper + `existsByUser`) shared across methods. Note `AuthServiceImpl` still uses `jakarta.transaction.Transactional` with no `readOnly` — it's the outlier, don't copy it.
- Tests (plain JUnit 5 + Mockito, no Spring context): `UserServiceImplTest` (19), `UserControllerTest` (7, `MockMultipartFile` for the upload), `PasswordUpdateRequestTest` (4, `Validator`-based like `RegisterRequestTest`), `GlobalExceptionHandlerTest` (2 — first test of the handler). Two first-in-project test idioms: **`ReflectionTestUtils.setField(entity, "id", uuid)`** to give an unpersisted entity an id (`BaseEntity.id` has no setter on purpose — the same wall `EventReminderJobTest` hit and dodged with `times(N)`; here the id is part of what's asserted), and **`MockHttpServletRequest`/`MockHttpServletResponse`** for the filter test.

Frontend notes (not this repo):

- **`<img src="/api/users/me/avatar">` will 401**: browsers don't send `Authorization` on `<img>`, and the JWT is in `localStorage`, not a cookie. Fetch with the header, `response.blob()` → `URL.createObjectURL` → `src`. No `Cache-Control`/ETag on purpose — re-fetch after upload; a once-per-session image has no caching problem to solve.
- Every session alive at deploy time gets a 401 once (legacy email-subject tokens) — see Auth.

Open at the time of writing:

- **The Testcontainers layer has not yet been run against `V19`** — Docker was down on the dev machine for the whole build. 292 unit tests are green; `SchemaIntegrationTest` (which is what proves `byte[]` ↔ `bytea` passes `ddl-auto=validate` and that `V19` applies) must go green in CI or locally before merging. If `validate` rejects the column type, the fix is `@JdbcTypeCode(SqlTypes.VARBINARY)` on `UserAvatar.data` — not added preemptively.
- No `UserAvatar` integration test (cascade on user delete, UNIQUE) — same precedent as `llm_credentials`; `SchemaIntegrationTest` could gain a `fk_user_avatars_user` cascade assertion like the `V11` one if it ever matters.
- `MapStruct` warns `Unmapped target properties: "email, password, role, ..."` on `updateEntity` — that's the desired behavior (those must not be mapped); `@BeanMapping(ignoreByDefault = true)` + explicit `@Mapping`s would silence it and make the intent visible, not done because `HabitMapper`/`TaskMapper` live with the same warning.
